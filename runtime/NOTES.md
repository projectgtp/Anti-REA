# Anti-REA v1.0 — Runtime Notes

Date: 2026-11-23. Status: **compile-verified only (JVM + smali), never device-tested.**
Scope: universal Kotlin runtime, package `com.appcore.runtime`. No Bridge
code, no app code, no secrets. Python stdlib + Kotlin stdlib only, no new
dependencies. Nothing pushed to GitHub; nothing under
`~/workspace/bridge-marketplace/` was touched.

## What it does NOT do (honest limits)

- **No Frida stop.** Nothing here kills Frida, a debugger, or a runtime
  memory dump. Env checks and traps are signals that something is
  suspicious; a determined attacker with Frida can read values after
  decryption and can hide from these checks. Server-side checks remain
  the real enforcement (same limit as v0.1/v0.2). L102 (2026-11-23)
  makes a memory editor's work harder to do and easier to notice
  (TracerPid, maps markers, obfuscated values) — it does NOT stop a
  determined root attacker, and it does not catch GameGuardian's
  virtual-space (no-root) mode. See `docs/GAMEGUARDIAN.md`.
- **XOR is obfuscation, not strong crypto.** An attacker who finds both
  key parts can reconstruct the key. The blob's sha256 gives tamper
  evidence, not secrecy against a skilled static analyst.
- **Env checks are signals, not proof.** Emulator/root markers can appear
  on legitimate devices (e.g. test-keys builds); a clean `checkAll()`
  (0 suspicious) does NOT prove the device is uncompromised.
- **No device test.** JVM round-trip + smali generation are verified
  below. No install, launch, or on-phone run has happened for v1.0.
- **The provider never refuses.** If the app never reads
  `ReaGuardProvider.findings`, the checks change nothing at runtime —
  integration (below) is what makes them matter.

## Integration contract for the CLI

- **Smali output dir:** `runtime/smali/` — package path
  `com/appcore/runtime/`, 19 `.smali` files: `ReaRuntime`,
  `ReaRuntime$$ExternalSyntheticLambda0/1/2`, `ReaEnv`, `ReaEnv$Finding`,
  `ReaIntegrity`, `ReaIntegrity$IntegrityResult`,
  `ReaIntegrity$$ExternalSyntheticLambda0`, `ReaTraps` (`Honeypot`,
  `DelayedFailure`, `ReaDecoys`, `TripwireEvent` + `Honeypot$$ExternalSyntheticLambda0`),
  `ReaGuardProvider`, `ReaGuardProvider$Companion`, `ReaModBlock`,
  `ReaModBlock$Finding`, `ModBlockData`. The CLI copies this
  tree into the protected APK's dex (or merges `build/runtime.jar` via
  its own d8 step — the jar is also kept at `build/runtime.jar`).
- **Decrypt entry the CLI may call** (verified present in the smali):
  `ReaRuntime.decrypt(Ljava/lang/String;Ljava/lang/String;Ljava/lang/String;)Ljava/lang/String;`
  — args: `(blobBase64, keyPart1B64, keyPart2B64)`, returns plaintext or
  throws `IllegalStateException`. Companion signatures:
  `ReaRuntime.verifyIntegrity(Ljava/lang/String;Ljava/lang/String;)Z`,
  `ReaRuntime.verifyText(Ljava/lang/String;Ljava/lang/String;)Z`,
  `ReaRuntime.reconstructKey(Ljava/lang/String;Ljava/lang/String;)[B`.
- **Provider manifest entry** (CLI writes into the protected manifest):
  ```xml
  <provider
      android:name="com.appcore.runtime.ReaGuardProvider"
      android:authorities="${applicationId}.appcore.guard"
      android:exported="false"
      android:enabled="true" />
  ```
- **Optional dex-hash asset:** CLI may emit `assets/meta/dex.sha256`
  (one line: lowercase hex sha256 of base.apk). If absent,
  `ReaGuardProvider.dexCheckPassed` is null ("not checked"), which is
  normal — not a failure.
- **Reading findings from the app:** `ReaGuardProvider.findings`
  (`List<ReaEnv.Finding>`), `ReaGuardProvider.dexCheckPassed`
  (`Boolean?`), `ReaGuardProvider.initialized` (`Boolean`).

## Runtime audit (Agent C) — JVM audit + fixes — 2026-11-23

Scope: all 18 `runtime/*.kt` files read end to end, plus
`runtime/NOTES.md`, `GAMEGUARDIAN-FIX-REPORT.md`,
`FINAL-6-REPORT.md`. Fixes only inside `runtime/` (code +
`runtime/tests/`); `build_smali.sh` itself unchanged, only its
output rebuilt. No other directory touched, nothing pushed.
Kotlin stdlib + JDK only, no new dependencies.

### Findings fixed (10)

- **F1 — wrong exception type + divide-by-zero in key handling
  (`ReaRuntime.kt`, `reconstructKey`).** Empty key parts made
  `decrypt()` throw `ArithmeticException` (`key[i % key.size]`,
  divide by zero); mismatched lengths threw
  `IllegalArgumentException` from `require()`, while `decrypt()`'s
  contract promises `IllegalStateException` — callers catching
  only that (e.g. `ReaResStrings.decryptResource`,
  `ReaAssets.decryptAsset`) would see the wrong type. FIXED:
  `reconstructKey` validates non-empty equal lengths and throws
  `IllegalStateException`. Fail-before observed: `decrypt empty key
  parts: expected IllegalStateException, got
  java.lang.ArithmeticException: / by zero`.
- **F2 — whole-file read in `verifyFileSha256`
  (`ReaIntegrity.kt`) and `verifyConfigFileHash`
  (`ReaIntegrity2.kt`).** Both used `readBytes()`, so hashing a
  large APK allocated the whole file in RAM; `OutOfMemoryError`
  is an `Error`, not an `Exception`, so the "never throws" catch
  did not catch it and it escaped a check that promises never to
  crash the app. FIXED: streaming 8 KB digest
  (`ReaIntegrity.hashStreamSha256`); both callers use it, empty
  config files still fail. Fail-before observed: 512 MB file
  under `-Xmx128m` → `OOM-ESCAPED: OutOfMemoryError thrown out of
  verifyFileSha256` (exit 3); after: `VERIFY-RESULT: true`.
- **F3 — double-invoke in `callByReflectionOrDirect`
  (`ReaIntegrity2.kt`).** `invokeReflectively` returned null both
  when the method was missing AND when it legitimately returned
  null, so a null-returning or void method was invoked TWICE
  (reflectively, then via the direct fallback) — double side
  effects. FIXED: internal tri-state `ReflectResult`
  (`Found`/`NotFound`); the fallback runs only on `NotFound`.
  Public signatures unchanged. Fail-before observed on pre-fix
  code (rerun3, 2026-11-23, sections (a)+(c) skipped-variant
  run): `FAIL: null-returning method came back as 'fallback'
  (direct fallback ran)`; after: null/void methods invoked
  exactly once.
- **F4 — L43 substring false positives (`ReaEnv2.kt`,
  `appClonerDetected`).** `"dual"` fired inside `"individual"`,
  `"clone"` inside `"myclone"`. FIXED: whole-token matching
  (`containsCloneMarkerToken` — split on non-alphanumeric, a
  token must START WITH the marker). Real cloner names still
  fire: `parallel`, `dual`, `clone`, `dualspace`, `cloner`,
  `ParallelSpace`. Fail-before observed: `app-cloner:
  detected=true, want false (evidence: clone markers:
  path:'dual')` on `/data/user/0/com.example.individualapp`.
  Remaining documented false positive: a path segment literally
  named `"clone"` still fires — a name alone cannot tell an
  innocent folder called `"clone"` from a cloner path (signal
  only, never a refusal by itself).
- **F5 — partial plaintext dex left on disk
  (`ReaMethodLoader.kt`, `writePlaintextDex`).** A
  `writeBytes()` failure returned null WITHOUT deleting the file,
  leaving a half-written plaintext dex behind. FIXED: internal
  `writePlaintextFile(file, plain)` deletes the file on ANY
  failure. Fail-before observed with a verbatim copy of the old
  body writing to a `/dev/full` symlink: `BUG-CONFIRMED: old
  write returned null but left the partial plaintext file
  behind`; after: the link is gone and the call returns false.
- **F6 — plaintext left in memory after rotation
  (`ReaMethodDecrypt.kt`, both `rotate` overloads).** The
  decrypted `plain` byte array was never wiped after re-sealing.
  FIXED: `plain.fill(0)` in a `finally`. No JVM-observable test
  exists for wiping a local array — fixed by construction, no
  behaviour change, noted honestly here.
- **F7 — non-constant-time Java gate (`ReaNative.kt`,
  `javaGate`).** The old plain `==` short-circuited on the first
  differing character, leaking the mismatch position by timing,
  while the native gate it mirrors compares in constant time.
  FIXED: `ReaIntegrity2.hexEqualsConstantTime`. No behavioural
  fail-before exists for a timing leak; the test proves the
  verdicts are unchanged (correct hash passes any case, wrong /
  blank / malformed refuse).
- **F8 — unbounded catch-up in `ReaTimer.tick`.** A clock jump
  (device asleep for hours) with a short interval ran the check
  once per elapsed interval in a single call — thousands of
  invocations blocking the calling thread. FIXED: at most
  `MAX_FIRES_PER_TICK = 10` fires per `tick()`; when the cap is
  hit the timer skips ahead so the next check is one interval
  after now. Fail-before observed: `cap: tick fired 100 times
  for 100 due intervals, want 10`; after: 10 fires, skip-ahead
  to 101000, schedule resumes.
- **F9 — `open(sealed)` ignored the stored hashes
  (`ReaMethodDecrypt.kt`).** The `SealedMethod` carries
  `blobSha256Hex` / `plainSha256Hex`, but `open(sealed)` never
  verified them — only the embedded hash prefix was checked.
  FIXED: `open(sealed)` now verifies the blob hash before
  decrypting and the plain hash after; blank or mismatched
  hashes refuse. Safe: every legitimate producer (`seal()`,
  `tools/make_method_blob.py`, `transformer/crypto.py`,
  `anti-rea.py`) fills both hashes. Fail-before observed on
  pre-fix code (rerun3, 2026-11-23, sections (a)+(c) skipped-variant
  run): `FAIL: open(sealed) accepted a tampered blobSha256Hex`;
  after: tampered/blank stored hashes refuse, good seal + rotate
  open.
- **F10 — `Honeypot` / `DelayedFailure` not thread-safe
  (`ReaTraps.kt`).** `failureCount++` is a read-modify-write
  and `ArrayList`/`HashMap` writes from two threads can throw
  or lose events. FIXED: `@Synchronized` on all accessors.
  Fail-before observed, 3 round-sets: worst counts 7118–7584 of
  8000 failures and 1434–3407 of 4000 trips, plus a live
  `ArrayIndexOutOfBoundsException` thrown out of a `Honeypot`
  thread; after: exactly 8000 / 4000 in all 3 round-sets, 3 runs.

## Crash hunt — protected Bridge 2.16.0 APK crashes on launch (2026-11-23)

The protected 2.16.0 APK (sha256
`90c55f7b873f60be80bb6d1d4fed37fbec7ed91ea62f23968394211afe117dce`,
`bridge-marketplace/android/bridge-2.16.0-antirea.apk`) crashes on
launch on the user's Infinix Hot 60i, every launch; the plain
2.16.0 APK works. The crash was hunted from the code + the APK
itself (no device log was available). **Honest result: no crash
cause was found by static analysis.** Everything that executes at
launch was checked and exonerated; the fixes below (F11/F12) close
real fail-safety gaps but are NOT proven to be the crash cause.
The decisive next evidence is the device logcat — see the
checklist at the end of this section.

### What was eliminated (evidence, not claims)

- **Missing `assets/antirea/dex.sha256` does NOT crash.**
  `ReaGuardProvider.checkDexHash` catches the
  `FileNotFoundException` (inner `catch`), `expected` is null,
  the method returns null ("not checked"). Confirmed in the APK:
  the protected 2.16.0 APK contains `assets/antirea/res_strings.json`,
  `build.json`, `manifest.json`, decoys — and NO `dex.sha256`
  (the CLI never writes it; the dex hash lives only in
  `build.json`). Same for the 2.14.0 protected APK.
- **The native `.so` is never loaded at startup.** The APK
  contains `lib/arm64-v8a/libreagate.so` (7,144 B), but NO class
  in the APK references `ReaNative` except `ReaNative` itself —
  no `integrityGate` / `nativeGate` / `nativeVersion` call site
  exists. `ReaNative`'s class init (the `loadLibrary` call) never
  runs at startup. `reagate.c` itself was re-read: SHA-256 is a
  standard FIPS 180-4 implementation, the JNI entry points null-check
  their arguments.
- **All 44 injected `ReaRuntime.decrypt` triples decrypt OK.**
  Every (blob, part1, part2) triple feeding a `decrypt` call in the
  protected 2.16.0 APK's app classes was extracted from the
  disassembled dex and test-decrypted with the reference
  decryptor (`transformer/crypto.py`): 44/44 OK, 0 failed —
  including all 19 in `<clinit>` static initializers
  (`BridgeConfig` 4 → `https://mbbridge.onrender.com`,
  `http://10.0.2.2:8000`, `https://api.bridge.example`;
  `CertPinning` 7 → `mbbridge.onrender.com` + 3 cert pins;
  `StunClient` 1 → `stun.l.google.com`;
  `PrefsTunnelKeyStore` 1 → `tunnel.key.`;
  `PointsShopActivity` 1 → `https://t.me/goodxvampire`;
  `ModelsKt` 4 → `pts-100/500/1000/5000`;
  `PropertyReference.getReflected` 1 → a JetBrains issue URL).
  A wrong triple would throw `IllegalStateException` inside
  `<clinit>` → `ExceptionInInitializerError` → crash on launch;
  no triple is wrong.
- **Flattened launch-path state machines trace clean.**
  A symbolic tracer (`/home/hatch/tmp/audit-c/trace_flatten.py`,
  evaluates the constant opaque predicates, checks state
  in-range, no state-register clobber, termination at return)
  was run over the launch path: `MainActivity.onCreate`,
  `BridgeConfig.<clinit>`, `CertPinning.<clinit>`,
  `StunClient.<clinit>`, `PrefsTunnelKeyStore.<clinit>`,
  `PointsShopActivity.<clinit>`, `ModelsKt.<clinit>`, and all 16
  app methods `MainActivity.onCreate` calls — 0 defects. A full
  sweep over ALL 3,880 flattened methods in the APK's app
  classes found 6 flags, all confirmed FALSE POSITIVES of the
  tracer: the flattener reuses the state register as scratch
  inside a block and restores it to the next state constant
  before jumping back (e.g. `VpnActivity` `:pswitch_f6`:
  `iget-object v15, v15, ...->selectedText` then
  `const/16 v15, 0x9` / `0xb` before `goto :goto_2`). None of the
  6 is on the launch path. Runtime classes are NOT flattened
  (0 `packed-switch` in the APK's runtime smali) and all are
  present in the dex; the provider IS in the manifest
  (`com.antirea.runtime.ReaGuardProvider`, authorities
  `com.bridge.mvp.antirea.guard` in the OLD build).
- **No res-string placeholders in the dex.** `res_strings.json`
  has 1 entry (`developer_server_hint`); no `__REA` placeholder
  string exists in the protected dex, so no startup string can
  be a never-loaded placeholder.
- **Provider matches current source.** The provider smali in
  the APK has the same Exception-only catches as the pre-fix
  source — i.e. the shipped build has the F11 gap (below).

### Fixes from the hunt (F11/F12)

- **F11 — provider catches `Throwable`, not just `Exception`
  (`ReaGuardProvider.kt`).** `onCreate()` caught `Exception`
  only, so any `Error` (`NoClassDefFoundError`,
  `UnsatisfiedLinkError`, `ExceptionInInitializerError`,
  `VerifyError`, `OutOfMemoryError`, `StackOverflowError`)
  escaping ANY check in `onCreate` propagated out of provider
  init and killed the app on launch, every launch. FIXED: all 6
  catches in `onCreate()` + `checkDexHash()` are now
  `catch (e: Throwable)`. **Limitation, stated plainly: no
  concrete Error source was found in the provider path, so this
  is defense in depth, not a proven fix for the observed crash.**
  JVM test (`tests/CrashHuntTest.kt`): the provider itself
  cannot be instantiated on the JVM — the android.jar stub
  throws `RuntimeException: Stub!` on construction — so the
  onCreate path is verified by code inspection plus a pattern
  test proving a `Throwable` catch swallows an `Error` that an
  `Exception`-only catch lets escape (F11b). The test reports
  the stub skip explicitly (`NOTE: F11a … skipped, not a
  failure`) instead of pretending to cover it.
- **F12 — safe `nativeVersion` wrapper (`ReaNative.kt`).**
  `nativeVersion()` is a raw external fun with no wrapper: a
  direct call throws `UnsatisfiedLinkError` when
  `libreagate.so` is absent. Nothing calls it at startup in
  v1.0, but any future caller could kill the app that way.
  FIXED: new `nativeVersionSafe(): String?` — null (never a
  throw) when the `.so` is not loaded or the JNI call fails.
  JVM test: `nativeVersionSafe()` returns null without throwing
  on the JVM (no `.so`), `integrityGate` still falls back to
  the Java gate and passes/rejects correctly.

### Device-test checklist (what to get from the phone next)

1. **Get the crash log — this is the single most decisive
   missing evidence.** On a PC with adb, or in Termux:
   `adb logcat -d | grep -i -A 30 "AndroidRuntime\|FATAL"` —
