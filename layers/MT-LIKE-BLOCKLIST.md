# Anti-REA — MT Manager-like on-phone modder blocklist (L101)

Date: 2026-11-23. These are Android apps that can open, edit, and
repack a protected APK **on the phone itself** — no PC, no Termux.
L101 detects them at runtime and the protected app refuses the
sensitive action while one is present. Refuse-only: never deletes
anything, never kills another app, never harms the device.

## How a name gets in here

- **VERIFIED** = the package name appears in at least one citable
  source (APKMirror / Uptodown / APKPure / PGYER / Appteka / GitHub /
  developer site). Two independent sources where stated.
- **VERIFIED (single source)** = one citable source only. In the
  enforced list, flagged as such.
- **CONFLICT** = sources disagree; both values are recorded, the
  conflict is stated, and the risk of blocking the wrong app is noted.
- **UNVERIFIED** = no citable source confirms the package name. It is
  listed for the record and is **NOT** enforced — the runtime never
  blocks on it.
- **N/A (not an Android app)** = desktop / IDE tool with no Android
  package name. It cannot be detected by PackageManager and is not
  in the enforced list. It is still countered by the static layers
  (its desktop analysis reads blobs, not secrets).

A repack/clone of any of these apps can use a different package name
and evade a package-name check. That is a known, stated limit of
L101: it catches the official builds, not every clone. The running-
process check and known-directory checks are the second and third
signals for exactly that reason.

## Known working directories (second signal, read-only checks)

These folders are where the apps above keep their working files.
`ReaModBlock.checkKnownDirs()` only calls `File.exists()` on them —
it never reads, writes, or deletes anything inside.

## Android 11+ package-visibility limit (honest, read this)

On Android 11+, `PackageManager.getPackageInfo(name)` returns
"not found" for a package the app cannot see. An app can only see a
package if it declares it in a `<queries>` element in its manifest
(or holds `QUERY_ALL_PACKAGES`, which Play restricts). Anti-REA does
**not** auto-inject `<queries>` entries in this round, on purpose:
the entries would list the blocked package names in plaintext in the
protected app's `AndroidManifest.xml`, defeating the encrypted
blocklist. So on Android 11+ without host-app `<queries>` entries,
the installed-check degrades gracefully (returns "not installed")
and L101 falls back to the running-process + known-directory
signals. Host apps that want the full installed-check should add
the `<queries>` entries themselves; a CLI option to inject them is
PLANNED. This limit is also stated in `docs/SELF-PROTECTION.md`.

## False-positive tradeoff (stated plainly)

MT Manager, Apktool M, NP Manager and APK Editor are also legitimate
tools — a developer may have one installed for lawful work on their
own apps. L101 cannot tell "installed for lawful use" from
"installed to attack this app". If any blocked app is present, the
protected app refuses the sensitive action (login, buy, settle, key
generation) until it is uninstalled — it never blocks launch, never
deletes anything, and never touches the other app. That is the
tradeoff, and it must be disclosed to users of a protected app.
