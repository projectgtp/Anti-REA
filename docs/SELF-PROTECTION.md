# Anti-REA — Self-Protection (v1.0 + L101)

Date: 2026-11-23. How Anti-REA protects **itself**, what that does
and does not do, and how to use it.

## What is protected

### 1. CLI integrity self-check (Task 2a)

`anti-rea.py` hashes its own code tree at startup against
`anti-rea.manifest.json` (SHA-256 per file, 25 files) and refuses
to run ANY subcommand if anything is missing, added, or changed.
There is no `--skip-self-check` flag, on purpose.

- Manifest: `anti-rea.manifest.json` (regenerated 2026-11-23 after
  the L102/L103 fix; the old manifest was `3333bcb6…`). It holds
  hashes only — **no secrets**. The manifest's own current sha256
  is recorded in `GAMEGUARDIAN-FIX-REPORT.md`, not here — this file
  is itself in the manifest, so writing the manifest's hash into it
  would change the hash it records.
- Covered (25 files): `anti-rea.py`, `transformer/*.py` (4),
  `runtime/*.kt` (10, incl. `ReaModBlock.kt` + `ModBlockData.kt` +
  `ReaTrace.kt` + `ReaMemory.kt` + `ReaRepack.kt`),
  `runtime/build_smali.sh`, `layers/REGISTRY.md`,
  `layers/MT-LIKE-BLOCKLIST.md`, `docs/GAMEGUARDIAN.md`,
  `verifier/*.py` (3),
  `tools/make_manifest.py`, `tools/gen_modblock_blobs.py`,
  `tools/make_sig_blob.py`.
- Generate/regenerate ONLY with the separate script
  `python3 tools/make_manifest.py` — the CLI never writes its own
  manifest. After any legitimate edit to a covered file, run the
  generator again or the CLI refuses to run (that is the protection
  working, not a bug).
- The manifest must cover EXACTLY the files the CLI checks: if the
  manifest lists a different set than `SELF_CHECK_FILES` in
  `anti-rea.py`, the CLI refuses. Coverage cannot be silently shrunk.
- Check it any time: `python3 anti-rea.py self-check`
  → `SELF-CHECK OK: 25 files verified against anti-rea.manifest.json`.
- The L102/L103 fix (2026-11-23) added `ReaTrace.kt`,
  `ReaMemory.kt`, `ReaRepack.kt`, `docs/GAMEGUARDIAN.md`, and
  `tools/make_sig_blob.py` to the manifest and regenerated it. A
  1-byte flip in a COPY of `runtime/ReaTrace.kt` is refused with
  exit 2 (see `GAMEGUARDIAN-FIX-REPORT.md` for the evidence).

Verified 2026-11-23 (see `SELF-PROTECT-REPORT.md` for the evidence):

| Case | Result |
|------|--------|
| Untampered tree, `self-check` | PASS (exit 0) |
| Untampered tree, `layers --list` | PASS (startup gate does not break normal commands) |
| 1 byte flipped in a COPY of `runtime/ReaModBlock.kt` | REFUSED, exit 2, names the file |
| 1 byte flipped in a COPY of `anti-rea.py` | REFUSED, exit 2, names the file |
| Manifest deleted in a COPY | REFUSED, exit 2 |
| `layers --list` on the tampered COPY | REFUSED, exit 2 (gate covers all subcommands) |

tree was never modified for the test.

### 2. Runtime sources — same string-encrypt + REA-IR pattern (Task 2b)

- **Source audit (2026-11-23):** `grep` for real-secret patterns
  (`sk-…`, `AKIA…`, `ghp_…`/`gho_…`, `password = "…"`,
  `secret = "…"`, `api-key = "…"`) over `runtime/*.kt`,
  `transformer/*.py`, `anti-rea.py` → **0 matches**. The only
  key-like values in the tree are documented FAKES: the honeypot
  values in `anti-rea.yaml` / `tests/*.yaml`
  (`AKIAIOSFAKEEXAMPLE`, `sk-fake-…` — AWS's own example values,
  meant to be found; using one trips a server-side tripwire) and
  the fake endpoint `https://api-decoy.example.invalid/v1/admin`
  (`.invalid` TLD, cannot resolve). Encrypted blobs in
  `tests/*-rea-ir/*.json` and `runtime/tests/test_blob.txt` are
  ciphertext of invented test strings only.
- **L101 blocklist (the concrete application):** the 13 verified
  modder-app package names exist as **encrypted blobs only** in the
  shipped runtime (`runtime/ModBlockData.kt`, generated by

  **0 plaintext blocklist names** in `runtime/*.kt` (shipped files)

### 3. L101 itself (Task 1)

The on-device modder-app block is layer L101 (41st implemented
layer, 101 slots total). Full list + sources:
`layers/MT-LIKE-BLOCKLIST.md`. Runtime:
`runtime/ReaModBlock.kt` + `runtime/ModBlockData.kt`. Test:
`runtime/tests/ModBlockTest.kt` (JVM, PASS 2026-11-23). The
protected app refuses the sensitive action while a blocked app is
present — never deletes, never kills another app, never harms the
device. Known limits are stated in the blocklist doc (renamed
clones evade the name check; Android 11+ installed-check needs
host-app `<queries>` entries the CLI deliberately does not
auto-inject; GameGuardian randomises its package name and is NOT
blocked; a lawful install of MT Manager is blocked too — that
false-positive tradeoff is disclosed, not hidden).

## What is NOT protected (honest limits)

- **Python source can still be read.** `anti-rea.py` and
  `transformer/*.py` are plain Python. The self-check does NOT
  encrypt or hide them — it only detects that they were changed.
  Obfuscation is not encryption. Anyone with the tree can read the
  CLI code; that is normal for an open-source tool and is not
  claimed otherwise.
- **The manifest is UNSIGNED in v1.0.** It is a SHA-256 inventory,
  not a cryptographic signature: it detects accidental corruption
  and tampering by anyone who cannot also regenerate it. A local
  attacker with write access to the whole tree can regenerate the
  manifest too, and then the check passes. The check's real value
  is (1) catching accidental corruption / bit-rot, (2) catching a
  third party who tampered with the CLI without access to the
  manifest step, and (3) letting a release be compared against the
  published release manifest (e.g. the GitHub release's manifest
  hash). A real signed manifest (Ed25519, public key shipped in
  the repo, private key held by the releaser) is PLANNED for the
  service phase — it cannot be done with stdlib-only Python and no
  secret in the repo, which is why it is not faked here.
- **The shipped APK runtime, not the Python CLI, carries the
  secrets.** The CLI's job is to encrypt needles into blobs; the
  runtime's job is to decrypt them in memory on the device. If an
  attacker runs the protected app under Frida or dumps its memory,
  they can still read values after decryption — that is the same
  limit as every other layer (stated in `layers/REGISTRY.md`).
- **No device / Frida live test.** Everything in this document is
  compile-verified and JVM/unit-verified only, never device-tested
  — same as all of v1.0. The user's reverse-engineering contact is
  the planned real red-team test.

## Workflow (for anyone editing this tree)

1. Edit the code.
2. `python3 tools/make_manifest.py` — regenerates the manifest.
3. `python3 anti-rea.py self-check` — must print SELF-CHECK OK.
4. If the CLI refuses with a hash mismatch, either the file was
   tampered with (investigate) or you edited it and forgot step 2
   (regenerate). Never hand-edit `anti-rea.manifest.json`.
